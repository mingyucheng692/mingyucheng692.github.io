## 超出调度预算的 RTT

被测网关基于 TI AM64x（2×Cortex-A53 @ 1.0GHz 级，Linux 6.12 `PREEMPT_RT`）。场景是一类常见的工业协议转换部署：端到端链路为"上层调度系统 →（北向协议）→ 网关 →（南向 Modbus）→ 多台总线设备"，上层以百毫秒级周期轮询控制，一条指令从下发到总线设备生效需在百毫秒内完成——约半个轮询周期。网关是链路的中间节点，两侧协议段的时延占比必须足够小，否则单是网关就会吃掉链路预算的大头；本次排查的目标，即确认网关侧时延是否低到不阻塞该预算。本文以 200ms 调度周期、1 主 4 从（RTU 侧两路 RS-485 总线各挂 2 台）为代表性调度参数与拓扑——参数为本文选取的测试基准，不指代具体项目。用探针工具对 Windows 11 Pro 上的 ModbusTools Modbus Slave 模拟器（默认参数，未设响应延迟）做首轮时延测试，结果与调度预算直接冲突：

- Modbus-TCP：RTT 在 30–60ms 之间抖动
- Modbus-RTU：RTT 在 50–80ms 之间抖动

按单台 50ms 估算，单路总线两台设备轮询一遍就要消耗半个调度周期，四台集中到一条总线则直接占满；链路口径更直接——单条指令 50–80ms 已占掉百毫秒级预算的大半。若这些数字反映网关的真实性能，链路时延要求无法达成，通信架构需要重新评估。但下结论之前，先确认一个问题：这 30ms 测的是谁？

## 先拆测量口径：RTT 里装了什么

翻探针源码，计时区间把 `Connect()` 整个包了进去：

```cpp
const auto t_start = std::chrono::steady_clock::now();
const auto conn_res = transport.Connect();  // socket 创建 + TCP 三次握手
// ... Send / Receive ...
const auto t_end = std::chrono::steady_clock::now();
```

也就是说，每一次"RTT"都包含 socket 创建与完整的 TCP 三次握手；RTU 侧同理，每轮都 `open()` 串口节点、`tcsetattr` 重置 termios、测完 `close()`。而生产环境的通信引擎是启动时建连一次、整个运行期复用的长连接，串口句柄常驻——每个周期只有纯 `Send → Receive`。

先修口径再测：计时起点收缩到 `Send()` 紧邻前一行，终点为接收完成后一行；TCP 改长连接常驻，RTU 串口打开一次常驻；循环模式输出 min/max/avg 统计。改造顺带测出了建连开销的实测值：`[CONNECT]` 1.29ms、`[OPEN]` 0.88ms——此前对握手与串口开关耗时的估算（分别为 20–30ms、5–10ms 量级）被实测证伪，建连环节的嫌疑就此排除。复测结果：

- TCP：平均 17.89ms（14.76–37.36）
- RTU：平均 52.18ms（34.40–67.27）

建连开销摘掉了，数字仍然偏高，说明时延大头在响应路径上。接下来分两步走：先换掉对端，证明板端清白；再回头解释对端为什么慢。

## 三步正交隔离回环

自造对端：一个 0-sleep 极简 Modbus Slave（收到 FC03/FC06 立即回包，单次内存业务耗时微秒级，开 `TCP_NODELAY`），交叉编译上板。然后按"由内向外、逐层加介质"的顺序做三步回环，每步只引入一个新变量：

| 步骤 | 拓扑 | 引入变量 | 预期 |
| --- | --- | --- | --- |
| 1 | `127.0.0.1` 本机回环 | 无 | < 0.3ms |
| 2 | `net5` ↔ `net6` 网线对插 | 网卡控制器 + 总线 | 1–2.5ms |
| 3 | RS485_0 ↔ RS485_1 跳线对接 | UART + 收发器切换 | 8–15ms |

三个预期只有 Step 2 压线命中，两个 miss 同样有信息量：Step 1 的 `<0.3ms` 是按桌面级 CPU 估的，1GHz 低功耗核上几次上下文切换加系统调用就是这个量级；Step 3 的 8–15ms 是按插入 t3.5 等待的常规从站估的，0-sleep mock 把这部分压掉了——预期错在哪一层，增量就归因到哪一层。

### Step 1：本机回环 —— 0.69ms

平均 0.69ms（0.47–1.28）。对端为 0-sleep 即时响应，处理路径是纯内存 PDU 解析加一次 `send` 系统调用，开销在微秒级；RTT 主体为两端内核 TCP/IP 协议栈路径。软件栈排除嫌疑。

### Step 2：双网卡网线对插 —— 1.02ms

平均 1.02ms（0.78–1.64）。减去 Step 1 的软件基数，AX88796B 网卡经 GPMC 总线的中断与搬移只引入 0.33ms 硬件路径增量。这一步踩了四个坑，都有记录价值：

1. **弱主机模型**：同一台 Linux 的两张网卡互发报文，内核发现目标是本机 IP，直接走 `lo` 环回捷径，电信号不经过网线。标准解法是把对端网卡关进独立网络命名空间，强制走物理口：
   ```bash
   ip netns add ns_eth6
   ip link set net6 netns ns_eth6
   ip netns exec ns_eth6 ip addr add 192.168.66.2/24 dev net6
   ip netns exec ns_eth6 ip link set net6 up
   ```
2. **发起端没 up + 跨网段**：`net5` 默认 DOWN，且两侧配成不同 /24 网段后 SYN 匹配不到直连路由，被默认路由从调试网口漏到交换机上，报 `Connection timed out`（探针 1 秒超时耗尽）。一根网线没有三层路由，两侧必须同网段，两端网卡都要 up。
3. **PHY 自协商瞬态**：链路 up 后前两个 ping 包丢失、第三包显示 2049ms——这与 PHY 自协商 1.5–2 秒、再叠加 ping 把 ARP 排队时间计入 RTT 的机理相符（推断，未单独隔离验证），稳态复测即回落到 0.4ms。首包异常不等于链路故障。
4. **网卡"消失"**：测试完 `ip netns del` 后 `net6` 在主命名空间找不到——有进程仍驻留在被删命名空间里，内核会把它保留为匿名命名空间扣住网卡。用 `/proc` 比对命名空间 inode 定位占用进程：
   ```bash
   for pid in $(ls /proc | grep '^[0-9]'); do
     if [ -e "/proc/$pid/ns/net" ] && \
        [ "$(readlink /proc/1/ns/net)" != "$(readlink /proc/$pid/ns/net)" ]; then
       echo "占用者: PID $pid ($(cat /proc/$pid/comm))"; kill -9 $pid
     fi
   done
   ```

### Step 3：双 RS-485 跳线对接 —— 4.15ms

两路 RS-485 口均为板载原生 UART（内核 8250 驱动族接管），与 Windows 台架的 USB 转接路径形成对照。平均 4.15ms（3.97–4.44），抖动 0.47ms。物理量纲核算（115200 8N1，每字节线上占 10bit）：

- 主站请求帧 8 字节：80bit ÷ 115200 ≈ 0.69ms
- 从站响应帧 25 字节：250bit ÷ 115200 ≈ 2.17ms
- 线传合计 2.86ms

实测 4.15ms 减去线传，附加开销 1.29ms。这笔账里没有协议帧间隔：对端源码为 0-sleep 即时响应，收齐完整请求帧后不插入 t3.5 等待、立即回包（规范对高于 19200 的波特率建议取保守固定值 1.75ms——若存在，仅"线传 + t3.5"就达 4.61ms，已超过实测均值，可独立佐证）。1.29ms 为两端 UART FIFO 中断、驱动、收发器换向与进程调度的收发路径开销合计（减法归账，未逐项分解）。线传 2.86ms 占实测均值约七成；对 1.29ms 的收发路径开销，本文未做压缩尝试（FIFO 水位、中断线程化等），不对其可压缩性下结论。

## 15.625 与 16：从机理假设到变量干预

板端清白已证，回头解释总表前两行对照组：对端为什么慢，慢的形态为什么恰好是那样。把两个最小值与已知的系统常量做量纲比对，确实能对上。但"对得上"和"被证明"之间隔着变量干预——这一节记录假设如何构造、干预怎么做、以及干预结果如何反过来修正假设。

假设的构造：

- **TCP 侧**：Windows 桌面系统默认定时器分辨率约 15.625ms（1000ms / 64Hz）；未提频时，`Sleep`、`WM_TIMER` 这类等待会被量化到该粒度。若 GUI 模拟器的响应路径包含此类等待（例如定时器驱动的收包轮询），RTT 下限就会被抬到一个滴答附近。实测最小 14.76ms、平均 17.89ms、最大 37.36ms（约两个滴答加处理开销），与"周期约 15.6ms 的响应环节"这一模型相容。反过来说，阻塞 socket、IOCP、事件对象都能被网络完成立即唤醒，若模拟器走这类路径，下限应在毫秒级（链路 ping `<1ms`）——实测下限 14.76ms 已经排除了"立即唤醒"类路径，响应路径上确实存在约 15ms 周期的环节。
- **RTU 侧**：转接芯片确认为 FTDI FT231X（VID `0x0403` / PID `0x6015`，驱动 `ftser2k.sys` v2.12.36.20），其驱动 Latency Timer 默认 16ms——短帧从首字节起算在芯片内等待超时后才上报主机（是超时 flush，不是"凑满一个包"；缓冲提前填满则立即上报，本测试帧长远小于该阈值）。叠加对端调度约 15.6ms，再加本测试帧配置的纯线传时间（FC03 读 10 寄存器：请求 8B + 响应 25B ≈ 2.86ms），合计约 34.5ms，与实测最小值 34.40ms 仅差 0.2ms。

随后完成的变量干预，结果分三类：

1. **FTDI Latency Timer 从 16 改为 1**（设备管理器 → 端口属性 → 端口设置 → 高级）：RTU 均值从 51.89ms 降至 45.51ms——只降 6.38ms，远小于单因素模型预期的约 15ms。机理被证实存在，但有效系数更小：Latency Timer 设为 1ms 不等于芯片真的按 1ms 上报，USB 批量传输的调度节奏给有效刷新间隔划出了下界。单因素模型就此证伪，台架实测下界同时锁定在 45–50ms——在本台架配置（FT231X 转接芯片、ftser2k v2.12.36.20 驱动、默认参数模拟器）下，继续调优 Windows 侧未再观察到边际收益。
2. **禁用 USB LPM 与选择性挂起**：复测 51.42ms，与干预前同轮基线 51.89ms 的差异落在轮次间波动范围内，无实质影响——RTT 仍在 45–50ms 台架带内波动。
3. **拓扑排除**：转接器经 Genesys GL850G Multi-TT Hub 接入，每个下行口有独立 Transaction Translator，同口全速/低速设备竞争可排除。

系统时钟粒度一项没法这样干净地判定。实测当前系统定时器周期已激活为 1.0ms（可编程下限 0.5ms），看似能否定 15.625ms 量化假说；但 Windows 10 2004 起 `timeBeginPeriod` 改为按进程生效，系统级读数不能保证模拟器进程内的等待原语同样按 1ms 调度。判别实验应当在模拟器进程上下文内提频后再看下限是否落到毫秒级——该实验无法从外部实施，约 15ms 节奏的具体来源（模拟器自身的定时器选择，还是软件内置的响应延迟）保持在应用层黑盒内。

ping 旁证的支持范围也要划清：Windows ping 网关 `<1ms` 证明物理链路健康、时延产生在对端主机内部；反向网关 ping Windows 100% 丢包只是 Windows 防火墙默认禁 ICMP 回显，与 502 端口无关。它支撑"瓶颈在对端"，不支撑任何具体时钟机理。

另有一个独立样本可交叉验证台架模型：同一对端上一次 FC06 控制写实测 RTT 63ms、重试 0 次。拆解为：

- 线传：请求帧与回显帧各 8 字节，约 1.38ms
- t3.5 帧间隔与收发器换向：按估计值 1.5–2.0ms（该对端实现未公开，取规范保守值）
- 板端开销：按 Step 3 实测附加开销（两端合计 1.29ms）折半估取 0.5–0.7ms
- 剩余约 59ms：落在 Windows 与 USB 转接一侧

后三项为估计或减法归账，非独立验证；t3.5 与板端两项属量级闭合而非精确归因——多参数拟合一个观测值不构成因果，恰是后文"可搬用的方法"第 2 条所警示的场景。Windows/USB 侧占比超过九成，与读事务 45–50ms 的台架带处于同一量级。

本节结论因此分两层：探针读数的大头来自测试对端——这一点由前文三步回环的替换实验证实；对端内部，USB 转接缓冲一项经干预证实存在但收益有下界，台架实测下界 45–50ms；模拟器应用层约 15ms 的节奏保持黑盒。

两条旁注：真实总线设备的控制器多为 MCU 裸机固件，硬中断响应，协议处理通常 1–3ms（行业经验值，非本文实测），模拟器 15ms 量级的下限通常不会构成真实设备的同量级约束，但慢响应的真实从站同样存在（如组态软件编写的 PLC、带协议网关的变频器），本文未做验证；把模拟器搬进 WSL2 或虚拟机通常也无本质改善——Hyper-V 虚拟交换、VM-Exit 与宿主时钟调度会引入新的时延层。

## 总成复验：从单次事务到一个调度周期

Step 1–3 回答"一次事务多少钱"，调度关心的是"一个周期够不够"。把自研调度引擎按代表性调度参数跑 10 秒有界总成：4 逻辑从站、200ms 轮询周期、100ms 超时、典型遥测帧型（单事务响应 137 字节）、4 路齐备后原子提交。对端为板端 mock slave。RTU 侧用单总线挂 4 个 Slave ID 时分轮转——代表性部署为两路 RS-485 各挂 2 台，单总线 4 从是比该部署严苛一倍的压测拓扑，余量结论对该部署只会更宽松；TCP 侧因板载测试网口只有两个，以 2 个物理端点承载 4 个 Unit ID（主站仍为一个，逻辑拓扑不变）。

结果：TCP 50/50 轮齐备提交，RTU 47–48/50 轮齐备提交；`ALL_READY`（引擎的从站在线状态标志，与逐轮齐备提交分属两个口径）全程保持。两个数字与机制一致：TCP 四通道并发互不影响；RTU 单总线时分，一次超时重试（100ms 超时等待，加一次约 14ms 的重试事务——单事务耗时核算见下节）即占去 200ms 周期的过半，连续两次超时则超出整个周期——个别掉轮符合启动对齐、写注入或偶发重试这类一次性事件的特征，具体触发点未逐轮标注。从成绩形态看，稳态吞吐不足可以排除：若每轮都超周期，成绩会稳定在低位且不会出现满额 50，而不是大多数轮满额、偶尔 47–48。

按该帧型核算 RTU 一轮的物理下限：单事务线传 0.69 + 11.9 ≈ 12.6ms（请求 8B + 响应 137B），4 从站一轮 ≈ 50.3ms，占 200ms 周期的 25%。这是纯线传下限；把 Step 3 小帧实测的 1.29ms 附加开销按事务平移估算，单事务约 14ms、一轮约 56ms——该开销含 FIFO 中断与换向等按事务计的成本，大帧下可能略增，精确值留待实际点表单包实测。即使按估算值，周期余量仍超过 70%。而这还是严苛拓扑下的账：代表性部署形态为两路 RS-485 各挂 2 台，单路一轮线传 ≈ 25.2ms（平移估算约 28ms），只占 200ms 周期的 13–14%——Step 3 的"线传为主"结论在系统层依然成立，对该形态余量更宽。

回到最初的问题——30–80ms 高时延是不是 ARM RT-Linux 网关侧的问题——在本次测试条件下，证据链给出的答案是否定的：组件级（三步回环：双网口 TCP 对发约 1ms、双 RS-485 对发约 4ms）与系统级（200ms 周期总成满轮运行）两层均未观测到网关侧瓶颈，高时延来自台架对端（Windows 主机、USB 转接器与模拟软件）。对照排查目标——网关侧时延是否阻塞端到端链路预算——按两个口径闭环：链路时延看单事务，实测 1.02ms（TCP）/ 4.15ms（RTU 小帧）、大帧估算约 14ms，相对百毫秒级链路预算占比约 1%–15%；调度吞吐看整轮，4 从站约 56ms、200ms 周期余量 70% 以上。两个口径下网关侧均不构成阻滞项。结论边界需注明：隔离与总成的对端均为 Mock，测试为空载单事务口径、总成为 10 秒有界窗口，未覆盖北向并发、长时间运行等更接近现场的负载形态；北向协议段（上层系统到网关）的时延特性不在本文测量范围内。通信基础设施（南向段）在此基线下不再是阻滞项。

（计数口径教训：这套总成的早期统计曾把 1ms 调度 tick 误计为事务轮次，产出过虚高约两个数量级的吞吐数字；修正后的口径是"4 路齐备原子提交"。先定义"一次"是什么，再谈数字——与测量口径问题同构。）

## 结论与工程产出

- 归因结论：首轮 30–60ms（TCP）/ 50–80ms（RTU）抖动与口径修正后的复测结果，均可归因于测试对端——替换对端后各层抖动均收缩到 1ms 以内（峰−峰），被测板在各层实验中均未呈现瓶颈，串口链路约七成为线传物理耗时。对端内部经变量干预确认：USB 转接 Latency Timer（16→1，均值降 6.4ms）收益存在实测下界，台架实测下界 45–50ms；模拟器应用层约 15ms 的响应节奏保持黑盒。
- 超时阈值参考基线：Modbus-TCP 建议 15–25ms、Modbus-RTU 建议 30–50ms。裕度口径需明示——以网关自身开销为分母（TCP 1.02ms / RTU 4.15ms）时为 15–25 倍 / 7–12 倍；但超时须覆盖对端响应，计入真实从站处理 1–3ms 与 RTU 侧 t3.5（约 1.75ms）后，端到端事务的实际裕度大致减半（TCP 约 4–12 倍、RTU 约 3–7 倍）。超时阈值不宜放大到数百毫秒量级——单点设备掉线需要在数十毫秒级被调度循环识别并切除。
- 基线使用约束：其一，以真实从站响应显著快于 Windows 模拟器为前提；其二，RTU 30–50ms 低于 Windows 台架实测 RTT（45–80ms），联调阶段若仍以 Windows 模拟器为对端，应沿用总成的 100ms 配置。该基线较 100ms 保守配置收紧，落地前需经现场联调验证。
- 调度预算：按比代表性周期（200ms）严苛一倍的 100ms 口径核算（总成实际按 200ms 运行），单次事务占比 TCP 1.02% / RTU 4.15%；多从站一轮物理下限核算见上节——严苛压测拓扑（单总线 4 从站）一轮约 50.3ms（200ms 周期余量 70% 以上），代表性部署（两路总线各挂 2 台）单路约 25.2ms。
- 如果不得不用 Windows 模拟器做功能联调（本台架转接芯片已确认为 FTDI FT231X；CH340/CP2102 无此设置项）：设备管理器 → 端口属性 → 端口设置 → 高级 → Latency Timer 从 16 改为 1。本台架实测均值由此下降约 6.4ms（51.89→45.51），收益存在 USB 调度下界，不要按理论值 15ms 预期。功能联调可用，但不宜作为性能评估的对端——至少在本台架（默认参数、未设响应延迟）的实测条件下如此。

## 可搬用的方法

1. **测量口径先于测量数据**。拿到一个性能数字，先问计时区间里装了什么：建连握手？设备 open/close？对端的调度周期？口径不定义，数据之间不可比。
2. **量纲吻合产出候选解释，变量干预才产出判定**。15.625ms、16ms 这类系统常量能把假设从凭空猜测升级为候选解释——本文的最小值比对排除了"立即唤醒"类路径；但多个可调参数拟合一个观测值不构成因果。判别方法是改一个变量（提频、改 Latency Timer、换转接芯片），看最小值是否随之移动。干预结果可以是非理想的——本文 Latency Timer 从 16 改为 1 只换来 6.4ms 降幅，单因素模型即被证伪；这同样是有效信息，它把排查指向下一个物理下界，而不是允许在原假设上继续加参数。
3. **变量正交隔离**。怀疑全链路时，从纯软件到物理层逐层加介质：localhost 定软件基数，物理直连测硬件增量，总线对接分离线传与附加开销。每一层的增量都可单独归因。
4. **模拟器不等于被测对象**。GUI 模拟器自带消息泵与系统时钟抖动，适合验功能，不适合评性能。性能验证用 0-sleep 极简对端，把对端开销压到可忽略。
5. **同机双网卡测真物理链路，netns 是标准手段**。否则弱主机模型会让报文在内核里走捷径，测不到物理链路。

在嵌入式 Linux 上做同类总线时延验证时，这套"口径修正 → 量纲比对与变量干预 → 三步回环"的流程和文中命令可以直接搬用。
